## Defects found

**D1 — one optional analytics event is still sent after consent is withdrawn (severity: low)**
Repro: enter `/pilot` with a user invitation → "Allow usage analytics" → on the feed, click "Withdraw consent" in the header (header then reads "Usage analytics: off") → navigate to `/pilot/feed`. The client POSTs `feed_viewed` to `/api/analytics`.
Observed: the request is sent; the server answers **200 with `{"accepted": false}`** — `ingestClientEvent` drops it because the session is no longer consented, so **nothing reaches Mixpanel** and the payload holds only `result_count` (no PII). A second navigation sends nothing further.
Impact: A14 says a withdrawn session "emits no optional events"; strictly, the browser still emits one, which the server refuses. No data exposure; a client-side consent-cache refresh would close it.
Evidence: `shots/A14-after-withdrawal-calls.png`, run log of `specs/13-withdraw-race.spec.ts` (`ALL_CALLS` shows `accepted:true, true, false`).

**D2 — upload validation errors are not in a live region (severity: low, accessibility)**
Repro: on the Evidence step choose a `.txt` or a 4 MB image. The message renders as a plain `<span class="fieldError">` referenced by `aria-describedby` on the file input, with no `role="alert"`/`aria-live`.
Impact: a screen-reader user is told only when the file input regains focus, not when the error appears. Sighted users see it immediately. Everything else on the screen (save failures, session loss, form errors) does use `role="alert"`/`role="status"`, so this is the odd one out.
Evidence: `shots/A16-unsupported-file-inline.png`, `A16-oversize-file-inline.png`; `components/reporter/EvidenceSection.tsx` around the `localError` span.

**No blocking defect was found.** Nothing in this run showed an exposure, data loss, false filing status or a misrepresented integration.
